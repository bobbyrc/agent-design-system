# Establish the design reference

## Inputs and authority

Use [the brief template](../assets/design-brief.md) to capture the requested deliverable, exact target surface and user task, audience, realistic content, platform constraints, success criteria, required states, and approval owner. Keep the target distinct from visual precedent: a screen cited as the visual-language reference does not become the redesign target. Preserve explicit target and direction choices; clarify only consequential gaps with bounded options through the harness's structured question capability, when available, before native design. Routine runtime assumptions can be recorded and verified without requesting approval again.

Inspect the current target and turn the findings into concrete problems and intended outcomes: what makes the user's task difficult, what should improve, and what evidence would demonstrate that improvement. Define which content and actions should receive emphasis, and why that hierarchy serves the task. Carry these criteria into option comparison and final review. Check existing product patterns, fonts, assets, tokens, and component APIs. Distinguish fixed requirements from open choices. Continue a settled direction without fresh exploration; a request to reproduce an already approved design can proceed directly to implementation.

When setting visual-quality targets, read [quality references and comparison](quality.md). Select applicable evidence as described there, reusing established inspected evidence where sufficient, then record specific mechanisms to transfer and observable targets in the brief. A reference is evidence for a quality, not authorization to copy its branding or assets. Obtain needed assets through authorized sources. Do not substitute a visually similar font or illustration silently.

For original design with open direction, produce two or three meaningfully different options using the same task and representative content. Compare task clarity, information hierarchy, readability, product fit, and expected behavior. Record the choice and requested refinements. Where the user has delegated direction selection, make that decision within the delegated criteria and document it. Escalate choices outside that scope. Avoid universal prescriptions about cards, colors, density, or motion. Give every primary option the same representative content, screen state, viewport configurations, and coverage. Label supporting state boards separately; do not present extra boards for a preferred option as an equal comparison.

## Native, inspectable design

Use editable text, named frames, reusable component instances and variants, variable-bound tokens, and native layout constraints. Reuse the project's system where one exists. When creating foundations, name semantic roles and map them to implementation tokens; document unresolved component/API gaps before dependent work.

Inspect actual rendered output after each coherent change. Before presenting, inspect the finished exports at the intended viewing size and fix observed legibility, clipping, alignment, or content defects. Confirm equivalent coverage across options; keep comparison labels and annotations outside the product UI. Editable structure and counts of frames, components, or tokens establish inspectability, not design quality. Check exact font availability and asset transfer early. An image of a UI can communicate direction but does not replace the required native, inspectable reference. Verify the available native write route and its permissions; report unsupported features instead of pretending a raster mockup is equivalent.

Show applicable loading, empty, populated, validation, error, selected, disabled, and overlay states. Specify responsive changes as rules, with representative narrow and wide configurations. Record navigation, keyboard/focus behavior, transitions, and accessibility expectations that static frames cannot describe. Use realistic long strings and relevant locales as stress cases, alongside the comparison fixture.

## Approval and freeze

Before acceptance, show how the reference addresses the target's observed problems and intended outcomes, with unresolved choices stated. A design-quality review evaluates whether it serves the task; an implementation-fidelity review later evaluates whether code matches it. A defect review that finds no blocking issue does not establish polished design quality. Judge whether the rendered hierarchy directs attention to the intended task, and whether readability, spacing, density, and visual consistency support it. Fix observed issues before recommending acceptance; unresolved user criticism keeps the direction unaccepted. Where project or user policy requires independent review, give a fresh reviewer the finished artifact and criteria, without the author's rationale or self-assessment.

Record the actual scope of each selection and continue authorized work. A style-only choice does not establish approval of the complete reference or permission to implement it. If the decision also approves concrete frames and states or authorizes their implementation, honor that scope without another approval ceremony. Keep unfinished screen-state selections `proposed` until approval covers their nodes, revision, and configurations; they need not block independent work on already approved states. Do not reopen choices already settled.

Record approval evidence in `design-decisions.md`: approver, date, selected node IDs and revision, approved configuration/state scope, criteria, and any exclusions. Do not label nearby alternatives approved. Preserve the selected screenshots, structured properties, literal text, font identities, and assets with provenance. Pin a retrievable Figma revision; if the tool cannot expose version history, preserve exports and metadata with hashes and record that limitation as the revision identity. A live URL alone is not immutable.

Create manifest entries for the agreed screen-state/configuration combinations using [the manifest template](../assets/manifest.example.json). Status is `proposed`, `approved`, or `superseded`; only evidence-backed selections become `approved`. The `capture` fields describe the reference conditions, while the adapter explains how to reproduce them. Mark gaps explicitly.

Stop dependent implementation when the approved selection, required font/asset, or behavior cannot be established. Resolve the gap through design within existing authorization. Reference writes, publication, and other external actions still follow the user's approval scope and harness permissions.
